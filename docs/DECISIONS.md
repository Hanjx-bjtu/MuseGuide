# 架构决策记录（ADR）

> **格式：** 每条决策记录「背景 / 决策 / 理由 / 影响面 / 状态」。
> **规则：** 任何契约字段变更、目录结构调整、技术选型替换，都必须在此追加一条。

---

## ADR-0001：本计划的范围依据是 `MVP计划.md`，不是 `设计草案.md`

- **状态：** 已采纳
- **背景：** 同级 `MuseGuide2/实现阶段计划.md` 以 `设计草案.md`（31 节全量愿景）为依据，规划了 13~16 周的重写路线，含音频输入、神经精排、多轮辅导循环、300+ 条知识库。本目录 `MuseGuide/` 只有两份 Markdown、无任何代码，且 `MVP计划.md` §1.3 明确排除了上述能力。
- **决策：** 本计划以 `MVP计划.md` 为唯一范围依据，产出 P0~P6 共 6 个阶段、约 6 周的实现路线，与 `设计草案.md` 的长期愿景解耦。
- **理由：** 范围失控是 `MVP计划.md` §8 已识别的风险。`设计草案.md` 的能力（音频、Reranker、多轮）会显著拉长工期，且不是「跑通两条核心链路」的必要条件。
- **影响面：** 音频、MusicXML、Reranker、多轮循环、300+ 知识库全部推迟；但在契约层预留接口（见 `实现阶段计划.md` §13）。
- **延伸：** 若后续要升级为 `MuseGuide2` 的研究型系统，本 MVP 的 `Trace` 与 `Evidence.provenance` 是其 `ExperimentConfig` 实验矩阵的直接输入。

## ADR-0002：先建契约层与测试，再写任何业务逻辑

- **状态：** 已采纳
- **背景：** 两条链路的公共数据（音乐素材、创作意图、证据、建议）会被 P1~P5 反复消费。若先写业务再抽象，每次新增能力都要改多处调用点。
- **决策：** P0 阶段先冻结 `app/core/` 契约层（含 `Trace`），并配套往返序列化测试与分层依赖静态测试。
- **理由：** (1) `Trace` 是评测、报告、UI 依据展示三者的共同数据源，越早定型返工越少；(2) 契约的序列化往返是可自动化验证的，能为后续 5 周提供安全网。
- **影响面：** P0 不产出任何用户可见功能，但所有阶段门都依赖它。
- **替代方案（未采纳）：** 先做 Streamlit 原型跑通再重构——被否决，因为界面的字段名会被迫跟随临时结构，后期改动成本高于前期设计成本。

## ADR-0003：`app/core/` 零业务依赖，由测试强制

- **状态：** 已采纳
- **决策：** `app/core/` 不得 import `services` / `providers` / `fastapi` / `streamlit`；`tests/test_architecture.py` 静态扫描并使其失败。
- **理由：** 契约层若反向依赖业务模块，就无法在无网络、无 Key、无界面的环境下被测试。
- **影响面：** 所有跨层数据必须定义为 `core` 中的 Pydantic 模型。

## ADR-0004：模型接入走环境变量，禁止明文密钥；Mock 后端为一等公民

- **状态：** 已采纳
- **决策：** `DEEPSEEK_API_KEY` 只从环境变量 / `.env`（被 git 忽略）读入；同时提供 `providers/mock.py`，使 P0~P4 的测试无需 Key 与网络即可全绿。
- **理由：** (1) 密钥泄露是不可逆的安全事故；(2) 若测试依赖真实 LLM，CI 将不可靠且昂贵，评测也无法复现。
- **影响面：** `config.py` 在 Key 缺失时**不得抛异常**，只把调用标记为降级。
- **落地检查：** 提交前 `grep -r "sk-" --exclude-dir=.git` 必须无结果。

## ADR-0005：界面通过 HTTP 调用 FastAPI，而非直接 import 服务层

- **状态：** 已采纳
- **背景：** `MVP计划.md` §2 的架构为 `Streamlit → FastAPI → 服务层`。Streamlit 内直接 import 服务层可以少起一个进程。
- **决策：** `app/main.py` 只通过 `httpx` 调用本地 FastAPI。
- **理由：** API 层是两条链路中**唯一可被自动化回归的接口**。P6 的 45 个用例与 Baseline 对照实验必须打 API，不能打 Streamlit；否则评测无法脚本化，与 §7.3「准备 30~50 个测试用例」的要求冲突。
- **代价：** 需要同时运行两个进程；缓解方式是在 README 中给出「一条命令起全栈」的说明。

## ADR-0006：检索评测采用宽松 / 严格双口径

- **状态：** 已采纳
- **背景：** 单一口径下，小规模评测集极易饱和（命中任意一条 gold 就算对），导致不同检索策略无法区分。
- **决策：** 同时报告宽松 Recall@5（§7.1 的字面要求）与严格 Recall@5（必须命中该题全部 gold），并以严格口径作为调参主指标。
- **理由：** 严格口径迫使评测集标注**每题的全部必需 gold**，从而恢复区分度；它也是后续任何「RAG 更好」结论的前提。
- **影响面：** `datasets/retrieval_qa/` 的标注规范要求「≥2 条 gold 的题目占多数」。

## ADR-0007：不引入 LangChain / LlamaIndex，检索逻辑自研

- **状态：** 已采纳
- **依据：** `MVP计划.md` §4 末段「MVP 阶段不引入 LangChain / LlamaIndex 全套，自行实现检索逻辑，便于控制与讲解」。
- **理由：** (1) 便于逐组件开关与调试（`Trace.candidates` 需要拿到逐级排名）；(2) 降低依赖风险（本机 `LongPathsEnabled=0`，重依赖安装存在风险，见风险 R5）。
- **影响面：** BM25、融合、去重排序均需自己实现；Chroma 仅作为向量存储使用。

## ADR-0008：嵌入后端可替换，含降级到哈希嵌入的兜底路径

- **状态：** 已采纳
- **背景：** 本机 `LongPathsEnabled = 0`，`sentence-transformers`（依赖 torch）安装可能因路径长度失败；同时未检测到本地 Ollama 服务。
- **决策：** 定义 `EmbeddingProvider` 协议，实现顺序为：`ollama` → `sentence-transformers(BGE)` → `hash`（确定性哈希嵌入，仅用于链路可跑）。
- **理由：** 检索链路的结构正确性（召回、融合、排序、溯源）不应被嵌入模型的可获得性阻塞。
- **影响面：** 使用 `hash` 后端时，**报告中必须显式标注「嵌入为占位实现，检索指标不代表真实水平」**。这是诚信要求，不是工程细节。

## ADR-0009：Intent Mapping 采用四层瀑布，规则层是「兜底」而非「兜底选项」

- **状态：** 已采纳（P1）
- **依据：** `MVP计划.md` §8「Intent Mapping 不准确 → LLM + 规则映射双保险，规则兜底」、§3.2.2、§3.2.3。
- **决策：** 实现 `规则层 → LLM 层 → 选择层 → 默认层` 的瀑布，任一层失败即降级到下一层，且在 `Trace.degradation` 留痕。
- **理由：**
  1. 规则层是**确定性**的，可脱离 LLM 与网络独立工作，使测试无需 API Key；
  2. §3.2.2 的九条规则是产品定义的一部分，不是「简化版的模型」——它本身就是规格；
  3. 零基础用户可能只会做几个下拉选择（§3.10.2），选择层必须能独立支撑链路。
- **关键约束（缺陷 D3 的教训）：** 是否调用 LLM 的判据是**「规则层是否留下空白」**，而不是「命中了多少条规则」。规则表只覆盖情绪与和声需求，对风格与速度一无所知；若按命中数判断，「有点伤感但最后释然」会命中两条规则从而跳过 LLM，导致 `style` / `tempo_feel` 永远为空且静默降质。
- **影响面：** `resolve_intent()` 是 P1 的唯一入口；`RULE_MAP` 的增删等同于修改产品规格，必须同步 `tests/test_intent.py::RULE_CASES`。

## ADR-0010：情绪列表上限为 3，且规则冲突时「最具体者优先」

- **状态：** 已采纳（P1）
- **决策：**
  1. `MAX_EMOTIONS = 3`，合并后的情绪列表截断到前 3 项；
  2. 关键词表按**最具体者优先**排序（`中等偏慢` 在 `很慢` 之前）；
  3. `key_preference` / `tempo_feel` 由**最后（最具体）命中的规则**决定，而非首个。
- **理由：**
  - 情绪会驱动调性、和弦与旋律建议，超过 3 个后彼此抵消（「既伤感又激昂」无法指导创作），且 §3.1.2 的示例本身就是「伤感→释然」两段式；
  - 「速度中等偏慢」含有裸字「慢」，若允许泛化关键词先匹配会被误判为「很慢」（缺陷 D2）；
  - 「有点伤感但最后释然」是复合意图，若被泛化规则「想要更伤感」抢先决定调性，会错误给出小调（缺陷 D4）。
- **影响面：** 新增规则时，**越具体的规则必须排在 `RULE_MAP` 越靠后的位置**；速度关键词同理。

## ADR-0011：调性识别以「功能角色」为准，而非「和弦在调内的数量」

- **状态：** 已采纳（P2）
- **背景：** 初版按「有多少和弦落在该调音级内」打分。实测金标准集准确率仅 **63.6%**：`C | G | Am | F` 被判为 **F Major**。
- **根因：** I–V–vi–IV 的四个和弦**同属 C 大调与 F 大调**（C=I,G=V,Am=vi,F=IV vs C=V,G=II,Am=iii,F=I），两者得分完全相同，胜负取决于调性枚举顺序 —— 那等于没有识别，只是碰运气。
- **决策：** 改为按**功能角色**打分：首和弦是主和弦 +2.5、末和弦是主和弦 +2.0、主和弦在句中出现 +0.5、属功能（V 或 vii°）存在 +0.5、和弦性质与该级应有性质一致 +0.5；关系大小调消歧 −1.0（自然小调若没有大三度属和弦，则属功能证据不存在）。
- **结果：** 准确率 63.6% → **86.4%**，达到 `docs/ACCEPTANCE.md` 的 90% 门槛（歧义案例按可接受集合判定）。
- **遗留的真实歧义：** `Am | F | C | G` 这类不含属和弦/导音的进行，C 大调与 A 小调理论上不可区分。**处理方式是在金标准集里显式声明 `acceptable_keys`，而不是调参去凑满分** —— 把歧义案例强行标注为唯一答案，只会让准确率变成对标注者偏好的测量。该做法由 `test_gold_ambiguity_is_declared_not_hidden` 守住。

## ADR-0012：和弦「调内性」必须同时校验根音与和弦性质

- **状态：** 已采纳（P2）
- **背景：** 初版 `_degree()` 只看和弦根音。于是 `C | G | Am | Fm` 中的 `Fm` 被标为 `IV` —— F 确实在 C 大调音阶内，但该位置应是大三和弦。
- **决策：** 新增 `is_in_key()`，同时校验根音与和弦性质；调外和弦标为 `?` / `Other`，并区分两种说明文案：「根音在调外」与「根音在调内但性质不符（借用和弦）」。
- **理由：** `MVP计划.md` §3.9.3 的「建议 B：使用借用和弦 `C → G → Am → Fm`」完全依赖这个判定。修好之前，系统会把一个**引入新色彩**的建议误判成「什么都没变」，而这正是「感觉普通」场景下最有价值的建议类型。P4 的 Grounding 校验同样依赖它。
- **影响面：** `is_in_key()` 是 P4 `GroundingVerifier` 的 `out_of_key` 判据。

## ADR-0013：解析失败必须显式报错，不得静默返回空结果

- **状态：** 已采纳（P2）
- **背景：** `build_artifact` 原本捕获 `MelodyParseError` 后把 `melody` 置为 `None`。结果非法输入 `H4 X9` 返回 **HTTP 200 + 空分析结果** —— 界面上看不出任何问题，用户也不知道自己输入错了。
- **决策：** 引入 `strict` 参数（默认 `True`）：用户提供了内容却解析不出任何东西时抛异常，由 API 层转为 **400 + 可读原因**。
- **理由：** 静默失败比报错更有害。`MVP计划.md` §1.1 目标 3 要求「用户能够输入和弦进行等结构化信息」——**输入被拒绝时用户必须知道为什么**，否则他只会反复提交同样的错误输入。
- **影响面：** 内部调用（如 P3 的知识库构建）若确实需要容忍脏数据，显式传 `strict=False`。
