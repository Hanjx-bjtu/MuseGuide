## 3. 指标口径

### 3.1 检索（`datasets/retrieval_qa/`，≥60 题）

| 指标 | 定义 | 目标 |
|---|---|---|
| 宽松 Recall@5 | 命中**任一** gold 即算对（§7.1 字面要求） | ≥ 0.90 |
| **严格 Recall@5** | 命中该题**全部** gold 才算对（本项目补充） | ≥ 0.70 |
| MRR | 首个 gold 排名的倒数，取均值 | 报告值，不设阈值 |
| 人工相关性 | 抽检 20 题 × 3 档（相关 / 部分相关 / 不相关） | 相关率 ≥ 0.80 |

> **为什么加严格口径：** 只有宽松口径时，评测集会饱和到 1.000，`hybrid` 与 `dense` 无法区分——这正是「无法证明也无法证伪」的根源。严格口径强制标注**每题的全部必需 gold**。

### 3.2 分析（`datasets/analysis_gold/`，≥30 片段）

| 指标 | 目标 | 说明 |
|---|---|---|
| 调性判断 | ≥ 0.90 | 手工标注为 gold |
| 罗马数字标注 | ≥ 0.85 | 逐和弦比对 |
| 终止式识别 | ≥ 0.85 | 仅在有终止式的片段上评估 |
| 旋律轮廓 | ≥ 0.85 | up / down / up-down / flat |

> **不做 NCT（非和弦音）检测指标**——`MVP计划.md` §1.3 排除了复杂乐谱分析，且该指标在 MVP 的输入范围（和弦文本 + 音名序列）内无法可靠标注。此项属于 v2 范围。

### 3.3 生成与建议（`datasets/advice_eval/`，≥20 题）

评分统一为 **1~5 分**，人工填写 `datasets/advice_eval/scores.csv`：

| 指标 | 含义（§7.2） | 目标 |
|---|---|---|
| Theory Validity | 理论上是否合理 | ≥ 4.0 |
| Relevance | 是否符合用户问题 | ≥ 4.0 |
| Explainability | 是否解释原因 | ≥ 4.0 |
| **Groundedness** | 是否有知识依据 | 编造引用数 = 0；调外和弦数 = 0 |
| Usefulness | 是否对创作者有帮助 | ≥ 3.5 |
| **Comprehensibility** | 对零基础用户是否可理解 | ≥ 4.0（零基础子集） |
| Actionability | 用户是否能据此行动 | ≥ 3.5 |

**零基础专项检查（§7.3）：**
- 输出中出现的专业术语必须在 `TERM_MAP` 内，或带通俗旁注
- 每条建议必须先说「听起来会怎样」，再说「为什么」（§3.8.3）

### 3.4 系统

| 指标 | 目标 | 采集点 |
|---|---|---|
| 端到端延迟 | ≤ 60 s | `Trace.timings_ms` |
| 结构化输出解析成功率 | ≥ 0.98 | `Trace.degradation` 中 `parse_failed` 占比 |
| 输出稳定性 | 同输入 3 次，结构一致 | 重复运行比对 |
| Grounding 捕获率 | ≥ 0.80（注入式） | 人为构造调外和弦 / 越界引用 |

## 4. 对照实验（§7.3）

| 组 | 说明 |
|---|---|
| **Baseline LLM** | 同一 prompt，**去掉** `[检索到的知识]` 段 |
| **MVP 系统** | Query 分解 + Hybrid 检索 + Grounding |

**报告要求：** 两组在 45 个用例上的七维评分 + 检索指标对照表。

> **⚠️ 提前声明的立场：** 若结论是「RAG 未显著提升建议质量」，**不得修改指标去凑结论**。
> 正确做法是：(1) 归因分析（检索精度问题 or 生成层未利用证据）；(2) 如实写入报告。
> 一个能测出自己系统边界的 MVP，比一个只能自证的 MVP 更可信。

## 5. 复现要求

任何进入报告的数字，必须满足：

1. 能通过 `knowledge/eval/run_eval.py --experiment <name>` 重跑
2. 对应的 `Trace` 已存档在 `experiments/<name>/`
3. 报告中标注：日期、模型版本、知识库构建 hash、随机种子
4. **报告中的所有数字由脚本从 `Trace` 渲染，禁止手工誊写**
