# 人工评分指南（SCORING_GUIDE）

> **对应交付：** P6 的 45 个人工评分用例（`MVP计划.md` §7.2 / §7.3 / §19）
> **评分材料：** `reports/scoring/samples.md`（输出原文）
> **评分表：** `reports/scoring/scores.csv`（每行一题，评分列留空待填）
> **汇总：** `python knowledge/eval/summarize_scores.py`

---

## 0. 先读这一节

**这份评分不需要你是音乐专业人士。**

八个维度里只有 `theory_validity`（理论上是否合理）需要乐理判断，
其余七个评的都是**普通读者的直觉反应**：

- 这个解释我看懂了吗？
- 它回答我问的问题了吗？
- 三个建议是不是其实在说同一件事？
- 我愿意照着它去改我的歌吗？

**如果你拿不准某一项 —— 留空。** 留空会在报告里显示为「未评」，
比随手填 3 分有价值得多：一个全是 3 分的表说明不了任何事，
而一张标注了「有 4 题我判断不了」的表能说明系统的边界在哪。

---

## 1. 评分流程（约 60~90 分钟）

```text
① 生成材料（一次性，约 3 分钟）
   python knowledge/eval/make_scoring_sheet.py

② 通读输出（约 20 分钟）
   打开 reports/scoring/samples.md
   先什么都别打，只读一遍，建立整体印象

③ 逐题打分（约 40~60 分钟）
   在 reports/scoring/scores.csv 里填
   建议一次只关注 1~2 个维度（横向扫描比纵向逐题更容易保持一致）

④ 汇总（1 分钟）
   python knowledge/eval/summarize_scores.py
```

> **为什么建议「按维度横向扫」而不是「按题纵向扫」：**
> 一次只评一个维度，评分标准在你的脑子里是恒定的；
> 逐题评八个维度，标准会漂移（前几题严格、后几题手松）。
> 这是人工评分最常见的偏差来源。

---

## 2. 八个维度怎么评

评分统一为 **1~5 分**。每档都给了锚点。

### 2.1 `theory_validity` — 理论上是否合理

> 这条建议在乐理上站得住吗？（**唯一需要乐理知识的维度**）

| 分 | 判据 |
|---|---|
| 5 | 手法正确、用例恰当，看不出问题 |
| 4 | 基本正确，有小的不规范但不影响听感 |
| 3 | 大致说得通，但细节存疑（如调式归属含糊） |
| 2 | 有明显错误（如把和弦功能说反） |
| 1 | 与乐理冲突，照做会出问题 |

**不懂乐理时怎么办：** 看机器校验结果（每题已标注「编造引用 N 条、调外和弦 N 个」）。
两者都是 0 且建议内容与知识库条目对得上 → 可给 4；否则**留空**。

### 2.2 `relevance` — 是否符合用户问题

> 它回答的是用户问的那件事吗？

| 分 | 判据 |
|---|---|
| 5 | 完全对准用户诉求 |
| 4 | 对准，但漏掉了诉求的一个侧面 |
| 3 | 有关但偏题（如用户问「结尾没落下来」，答的是「如何增加色彩」） |
| 2 | 基本跑题 |
| 1 | 答非所问 |

**例：** 用户说「保持温暖，但不要太普通」。
如果建议只讲「如何让和弦更复杂」而没提「保持温暖」，最多给 3。

### 2.3 `diversity` — 建议之间是否有差异（**仅多方案题**）

> 几个方案是**真的不同**，还是同一个改动的三种说法？

| 分 | 判据 |
|---|---|
| 5 | 手法本质不同（如：加音 / 换低音 / 借用和弦） |
| 4 | 方向不同，但有两个偏接近 |
| 3 | 三个方案都是「加七音」类的小变体 |
| 2 | 只有措辞不同，和弦几乎一样 |
| 1 | 完全重复 |

**这一项很重要**：如果三个方案其实一样，那「给用户 2~3 个选择」
就是虚假的选择权，比只给一个方案更糟。
单方案题请在 CSV 里**留空**。

### 2.4 `explainability` — 是否解释了原因

> 它说了「为什么」，还是只给了结论？

| 分 | 判据 |
|---|---|
| 5 | 每个选择都有原因，且原因与选择对得上 |
| 4 | 大部分有原因，个别是断言 |
| 3 | 有一半在讲「是什么」而不是「为什么」 |
| 2 | 基本只有结论 |
| 1 | 完全没解释 |

### 2.5 `groundedness` — 是否有知识依据

> 建议是否建立在可追溯的知识上？

| 分 | 判据 |
|---|---|
| 5 | 「理论依据」与建议内容明显对应，来源可查 |
| 4 | 有依据，但关联偏弱 |
| 3 | 列出了依据，但看起来是通用套话 |
| 2 | 依据与建议关系不明显 |
| 1 | 依据是编造的 |

**参考：** 机器已标注编造引用数。**只要 > 0 就直接给 1 分**。

### 2.6 `usefulness` — 对创作者是否有帮助

> 如果我是一个想写歌的人，这段内容对我有用吗？

| 分 | 判据 |
|---|---|
| 5 | 直接可用，我会照着试 |
| 4 | 有启发，需要自己再想一想 |
| 3 | 说得对但比较泛，帮助有限 |
| 2 | 像教科书摘抄，跟我的歌没关系 |
| 1 | 完全没用 |

### 2.7 `comprehensibility` — 零基础用户能否看懂

> 一个完全不懂乐理的人能读懂吗？

| 分 | 判据 |
|---|---|
| 5 | 全程日常语言，没有需要查词的地方 |
| 4 | 个别术语但配了通俗解释 |
| 3 | 有术语没有解释，但整体能猜 |
| 2 | 多处术语构成阅读障碍 |
| 1 | 基本读不懂 |

**提示：** 可以拿给身边不懂音乐的人读一段，问「你看懂它在说什么了吗」。
这比自我判断准得多。

### 2.8 `actionability` — 用户能否据此行动

> 看完之后，用户知道下一步做什么吗？

| 分 | 判据 |
|---|---|
| 5 | 明确给出可执行动作（换成什么和弦、怎么改） |
| 4 | 方向清楚，细节要自己补 |
| 3 | 知道该往哪走，但不知道具体怎么做 |
| 2 | 只是描述，没有可执行内容 |
| 1 | 看完不知道做什么 |

## 3. 常见评分偏差（请留意）

| 偏差 | 表现 | 对策 |
|---|---|---|
| **标准漂移** | 前几题严格、后几题手松 | 按维度横向扫，一次只评一个维度 |
| **光环效应** | 一处错得离谱就给全 1 分 | 各维度独立评，先评完 A 再看 B |
| **中心倾向** | 全填 3 分 | 逼自己在每题里找出「比平均好/差」的地方 |
| **知识诅咒** | 你懂乐理，觉得「这很通俗啊」 | `comprehensibility` 尽量找外行朋友试读 |
| **礼貌性高分** | 自己做的项目，不忍心打低分 | **低分比高分更有价值** —— 它告诉你要改哪里 |

> **这个项目的评分目标是发现边界，不是证明它好。**
> 一份全 5 分的评分表对项目的帮助，远小于一份标出了 3 个 2 分的表。

## 4. 评分表格式

`reports/scoring/scores.csv`：

```csv
case_id,kind,input,latency_s,theory_validity,relevance,diversity,explainability,groundedness,usefulness,comprehensibility,actionability,comment
gen.starter.001,starter,我想写一首关于毕业的歌…,6.2,,5,3,4,5,4,4,4,和弦走向常见但解释清楚
```

- 评分列填 **1~5 的整数**
- **留空表示无法判断**（会统计为「未评」，不计入均值）
- `diversity` 列在单方案题上**必须留空**
- `comment` 写一句话理由，尤其是给了低分的时候

## 5. 汇总会输出什么

```powershell
python knowledge/eval/summarize_scores.py
```

输出 `reports/HUMAN_SCORING.md`，包含：

- 各维度的**均值、中位数、最低分**，以及**评了多少题**
- 与验收门槛的对比（`docs/ACCEPTANCE.md` §3.3）
- **得分最低的 5 题**及其原输入（便于定位问题）
- 未评项统计（明确说明哪些维度数据不足）

> 报告会如实写明「**N 题未评**」。样本量太小或维度缺失时，
> 报告会提示「不足以支撑结论」，而不会给出一个好看的平均分。

---

## 6. 两人评分时的补充

如果有第二个人独立评分，汇总脚本会自动计算 **Cohen's κ** 一致性系数。

> `MVP计划.md` §7.2 的评估方法要求标注一致性校验。
> **κ < 0.6 时，汇总报告会明确标注该维度不适合用于结论** ——
> 这是「宁可承认指标不可靠，也不拿它当证据」的原则。
